01 / Control flow

Codex adds a tool-orchestration loop inside the model loop.

Default selection comes from the model, not just feature flags.

model_info.tool_mode is consulted first. Only an unspecified model mode falls back to code_mode_only, then code_mode, then direct calls. The first two global flags default off; that does not disable a model-selected mode.C38C40

In the pinned bundled catalog, 11 of 12 entries select code_mode_only, including GPT-6.1-Sol and GPT-6-Astra. GPT-5.5 leaves it unspecified. A fetched catalog or model override can differ; these counts describe the bundled baseline, not every live session.C39

Direct

Ordinary calls go from the model to tool handlers.

Code mode

Adds exec/wait alongside eligible direct tools.

Code-mode-only

Hides eligible nested tools from direct visibility; tools marked direct-only can remain outside the script.

These are three distinct exposure modes, not three different shell executors.C41C43C52

Pico: host-pumped state machine

  1. Build an immutable request snapshot

    Resolve the active provider, copy canonical input, filter tools, apply instruction and request-context hooks, and queue a worker request.P1P4

  2. Stream on a worker

    The provider emits display deltas; the host processes events. Streamed tool rows are not yet the executable batch.

  3. Ingest the completed provider result

    Validate and record assistant items and tool calls. Only then does StartNextTool dispatch pending calls.P2

  4. Settle the whole batch

    Run callbacks on workers; serialize apply/after callbacks on the host. Wait for every pending call before the next request.P3P22

  5. Continue or finish

    Tools cause a follow-up request. Without calls, the finish path checks compaction and queued steering before returning idle.P13

↳ The core consumes a provider-neutral result; provider code owns the wire protocol.

Codex: outer sampling, inner code cell

  1. Capture the step and its tool mode

    Build the Responses prompt and router. In code-mode-only, eligible tools become nested tools.* methods rather than separate direct-call specs.C30C38C43

  2. Dispatch the outer call during streaming

    A completed exec or other outer tool-call item normally starts dispatch immediately. Post-model hooks or a mailbox drain can defer dispatch.C2C3

  3. Execute JavaScript and nested tools

    The script can await calls, branch on their results, or start independent calls concurrently. Nested requests re-enter the host’s tool runtime; they do not require a new model response.C42C44C45

  4. Collect completion or a yielded cell

    Outer call results are collected after the response stream ends. exec may return a running cell; wait retrieves new output while that script continues.C29C42

  5. Continue sampling or finish

    Tool follow-up, pending user input, and completion hooks decide whether another model request is needed. Several nested operations may already have finished within one exec.C1C42

↳ exec is the JavaScript orchestrator; exec_command is a shell/process tool. They are different lifecycles.

One model call can contain a dependent tool workflow.

Pico’s native batch scheduler dispatches calls whose arguments the model has already supplied. Codex code mode can compute later arguments and control flow from earlier tool results within the same script.P3C42

Dispatch timing is a separate difference: Codex can begin an outer exec or direct call while the model response still streams; Pico starts its batch after the completed provider result. This is a control-flow distinction, not a measured latency advantage.C2P2
02 / Admission & ordering

Parallelism is a tool contract in both.

Pico batch: two eligible children, a shell barrier, then another call

PHASE APHASE BPHASE CCall 1child A ∥Call 2child B ∥Call 3sh · exclusiveCall 4later call
Schematic phases; not durations. Assumes capacity for two calls. “Parallel-safe” is a scheduling promise, not proof of independence.

Eligibility

Pico

Registration requires PARALLEL or SEQUENTIAL. The per-turn parallel-call cap limits admission; a sequential call waits for earlier running siblings and prevents later calls overtaking it.P3P23

Codex

Nested code-mode calls use a broker-owned ToolCallRuntime, which applies the shared-read/exclusive-write admission gate to handlers. JavaScript Promise.all can request overlap, but does not bypass runtime readiness or exclusive admission.C44C45C3

The shell differs

Pico

sh and all four background-job tools are registered sequentially within an agent’s batch. Separate agents can still operate on the same workspace concurrently.P5P6P22

Codex

The exec_command handler declares parallel support. Independent invocations can overlap. In code mode, await can order a dependent command after its prerequisite within one script; a separate model request is not required.C42C6

Delegation gate

Pico

Even though subagent is registered parallel-capable, each call additionally requires a known profile with parallel_safe: true. Unknown or malformed profiles become barriers.P3

Codex

Collaboration uses separate lifecycle tools rather than Pico’s profile parallel_safe gate. In V2’s default exposure configuration, these are direct-only model tools even in code-mode-only sessions; they are not ordinary tools.* methods.C48C52C12C14

04 / Trust & execution authority

Catalog restriction ≠ process containment.

Pico: offer, intercept, execute

Offered snapshot→Before hook→Tool worker

The request retains its filtered tool catalog. A call to an unoffered tool is rejected before tool code or hooks run. A before-tool hook can deny an offered invocation or rewrite permitted arguments.P4P3P9

The builtin shell forks, changes directory, and runs /bin/sh -c. This path does not install an OS filesystem/network sandbox. A workspace cwd is a starting directory, not an access boundary.P5

Interactive permission prompts are implementable through pico_tool_ask; the supplied permit_tool.c demonstrates a before-tool confirmation extension. That example is not a built-in mandatory shell approval policy.P10

Codex: policy plus execution environment

Tool policy→Approval→Sandbox / backend

Command policy derives an approval requirement from command analysis, permission requests, and approval settings. For dangerous unmatched commands, Never approval forbids rather than silently authorizing execution.C10

For restricted local execution, command transformation selects platform mechanisms: macOS Seatbelt, the Linux sandbox helper, or Windows restricted-token handling. Remote execution uses its backend path instead.C11

This is configuration-dependent enforcement, not an unconditional guarantee. Unrestricted permission profiles and approved additional permissions change the authority available to a command.

The code cell itself runs in a fresh V8 isolate with no Node, direct filesystem, network, or console access. Shell access is mediated by exposed tools.* callbacks and their handler policies; JavaScript orchestration does not bypass command approval or sandbox enforcement.C42C45

Pico’s read-only child rule is model-facing. A profile that permits sh permits that shell tool, not just read commands. Neither a tool allowlist nor parallel_safe prevents writes by the operating system.P11P5
05 / Delegation topology

Child lifetime and inherited context both differ.

Pico: task → result in one tool call

Parent: subagent(profile, task, session_id?)
Child runs its own model/tool loop
Parent tool resolves with the child’s result

The delegation worker waits while the host creates and pumps the child. A resumed call targets an exact previous child session; it does not import new parent-side history automatically.P11P22

New children start without the parent conversation. The task must contain the relevant paths, constraints, and requirements. Profiles can select model, effort, and exposed tools.P11

Codex V2: create → task name → coordinate

Parent: collaboration.spawn_agent(…)
Child starts; spawn returns a task name
Parent: send_message / followup_task / wait_agent / interrupt_agent / list_agents

V2 spawn awaits creation and input preparation, not the child’s completed task. By default it returns task identity without internal agent metadata; the namespace and exposure are configurable.C49C48C12

V2’s fork_turns defaults to all: the full-history fork is the default, while none starts without it. fork_context is explicitly rejected in V2. This differs from Pico’s fresh child context.C50

Child creation carries inherited environment bindings. Restoring an evicted V2 child revalidates cached bindings against current parent authority rather than restoring superseded permissions.C53C15

Agent-version selection is model- and session-dependent. Nine of the 12 bundled entries select V2; two select V1; one leaves it unspecified. Configuration can force V2 or disable agents. Otherwise an already-resolved session/history version is retained; for a new session, model metadata precedes the V1/disabled global feature fallback. Legacy restored history without version metadata retains V1.C39C46C47C51
V1 remains a separate contract. V1 exposes spawn, send_input, resume, wait, and close operations. Full-history inheritance is opt-in through fork_context, not V2’s default fork_turns: all. The global V2 feature flag defaulting off therefore does not imply that a model-selected session uses V1.C12C13C14C46

V2’s bundled configuration enables messaging/follow-up and wait_agent; flags can remove them. Its default non_code_mode_only: true keeps collaboration tools direct-only, so “code-mode-only” does not mean every operation must run inside JavaScript.C48C12C52

06 / Input, history & compaction

The transcript is not the next wire request.

Steering a busy turn

Pico

Accepted steering is queued and logged. It is delivered into canonical input at a settled boundary—after the batch, final response, or compaction—not by replacing the active provider request. Cancellation/error invalidates undelivered steering.P12P13

Codex

Pending input participates in the follow-up decision. A watcher can signal preemption; the supported interruptible Responses Lite path may drain the stream while preserving completed items before the next request. This is transport-dependent, not “every message immediately cancels generation.”C1C16C17

History vs request

Pico

JSONL records preserve conversation events. Request-context hooks add transient input that is not automatically canonical history; native provider state may also constrain which provider/account can replay the session.P1P15P16

Codex

Conversation items update history and rollouts; request projection can filter metadata without deleting saved history. Each completed exec uses a fresh isolate; store()/load() provide explicit cross-cell session storage instead of persistent JavaScript globals. A yielded cell remains alive until completion or termination.C18C30C42

Automatic compaction timing

Pico

The normal finish path checks the configured token threshold after a response without pending tool calls. The tool-batch continuation goes straight to the next request; it does not run that finish-path threshold check.P3P13

Codex

Compaction may run before sampling, at a follow-up rollover boundary, or through post-turn summarization. Those branches depend on token thresholds, window requests, and prepared candidates.C19C1C20

Replacement mechanism

Pico

A compact hook can supply text; otherwise a provider performs text or capability-gated native compaction. A text request that returns tool calls is retried without tools. Replacement waits for checkpoint persistence; failure retains prior context.P13P14

Codex

Local summary compaction and remote compaction paths coexist. Remote installation builds replacement history; guarded replacement checks the captured prefix/auth context, preserves an eligible live suffix, and persists a compacted checkpoint.C21C22C23

Persistence is not exact HTTP replay. Both save history separately from request construction. Current hooks, selected capabilities, and provider projection can alter a resumed request; neither implementation should be described as replaying its old wire bytes.
07 / Extension points & recovery

The replaceable boundary is different.

Extension runtime

Pico

C99 source files are compiled and loaded as shared libraries. pico_ext() separates host and workspace instances; workspace-local sources cannot declare host callbacks. Reload waits for affected runtimes to quiesce, while other workspaces remain usable.P18P19P22

Codex

The Rust extension API has typed, ordered contributors for native executors and tool lifecycle observation. MCP server contributions and selected-plugin overlays form a separate route into the tool plan. This is not Pico’s drop-in C source / dlopen lifecycle.C24C25C26

Provider protocol

Pico

A registered provider implements one streaming turn over canonical input/results. Builtins support OpenAI Responses and Chat Completions paths for Hyper/xAI; new providers can use the same registration API. Ephemeral turn transport state is separate from persisted provider history.P17P1

Codex

Custom provider configuration targets the Responses wire API. wire_api = "chat" is explicitly rejected in this release. Supporting an OpenAI-compatible Chat Completions endpoint alone is therefore insufficient for the stock provider path.C27

Pico retry ownership

Builtin provider recovery classifies transient failures, honors Retry-After, uses backoff/jitter, and has a 600-second recovery budget. Stream reset deltas separate retry attempts. These are provider-managed rules, not a universal retry guarantee for arbitrary registered providers.P20P17

Codex retry ownership

Sampling-stream recovery uses provider retry limits and error advice, with a possible transport fallback after exhaustion. An optional connection-retry feature can continue with unbounded backoff for eligible failures; that behavior is not the unconditional default.C28

Pico cancellation boundary

Cancellation is signaled to workers; force-cancel may retire a runtime, but checkpoint handling has special settlement rules. Background termination targets the owned command group; descendants that escape it are outside that ownership boundary.P21P28

Codex cancellation boundary

Turn cancellation and queued-input preemption are distinct. Sending a remote response-cancel operation requires the relevant feature, Responses Lite, and an interrupt handle. A yielded code cell has its own lifetime: wait can terminate it. Cancelling sampling or a cell does not reverse already executed tool side effects.C42C29C17
